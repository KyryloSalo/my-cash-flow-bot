# План наведення порядку

**Статус:** запропонований план, не вже виконана реорганізація. [Dashboard](README.md) · [Робоча модель](OPERATING_MODEL.md) · [Початковий реєстр](register.json).

## Принцип послідовності

Спочатку стабільна база й узгоджена поведінка, потім докази, потім спрощення коду. Не починати з масового переписування `bot_main.py`, розбиття всього фронтенду, введення нової платформи чи запуску шести постійних агентів. Це збільшить одночасну невизначеність.

Пакети нижче — порядок залежностей, а не обіцянка календарних строків. Тривалість оцінюється після першого characterization slice; доступність власника для бізнес-рішень і реального provider acceptance зараз не відома. Перший пакет має бути невеликим PR, а не багатотижневим «великим наведенням ладу».

## Пакет 0. Стабілізувати точку відліку

**Мета:** кожен агент розуміє, який код аналізує і що реально відправлено користувачеві.

- Залишити recovery-роботу недоторканою; порівнювати корисні локальні зміни з актуальним `origin/main`, переносити лише тематично після перевірки. Не merge recovery wholesale.
- Зв’язати `main SHA`, останній deployment evidence і наявний acceptance debt. Відокремити artifact deployed від feature accepted.
- Опублікувати цей docs-only пакет через звичайний PR/`validate`, коли власник дозволить commit/push. Production redeploy для нього не потрібен, якщо склад runtime artifact не змінюється.
- Вирішити, як вимагати незалежний review технічно: зараз branch protection має `validate`, але нуль required approvals. Для solo-owner не встановлювати механічно правило, яке унеможливить merge: обрати дозволеного незалежного reviewer/інший перевірний gate і перевірити точний candidate.

**Вихід:** одна доступна в GitHub стартова сторінка; видимі незакриті acceptance-питання; немає залежності від приватної recovery-папки. **Не вихід:** новий deployment або оголошення всього продукту стабільним.

## Пакет 1. Узгодити вимоги й джерела істини

**Мета:** агент не може вибирати з двох протилежних вимог ту, яку легше реалізувати.

1. Першим закрити конфлікт partner trial/card: що показуємо до логіну; що резервуємо; коли починається trial; що блокується до bind; як поводяться existing/paid/family користувачі; чи потрібне автоподовження. Поточна реалізація та затверджене бажання — окремі поля.
2. Визначити support policy Telegram: які фінансові сценарії лишаються підтримуваними, які лише ведуть у PWA. Не вимикати їх до рішення й аналізу залежностей.
3. Обрати канонічне місце компактних контрактів. Версіонувати актуальні вимоги в тому самому репозиторії, що й код; старим зовнішнім документам надати посилання/статус, а не підтримувати дві активні копії.
4. Довести початкову карту до повного контрольованого inventory: маршрути, callbacks, Celery jobs, зовнішні webhooks, стани PWA, таблиці й config **names**, пов’язані з FLOW/INV. Знайдені endpoints не прирівнювати до прийнятих сценаріїв.
5. Кожне неоднозначне правило — коротке рішення з власником і наслідком. Не змінювати фінансову поведінку в docs-only PR.

**Вихід:** затверджені контракти перших критичних сценаріїв; явний список unmapped/unknown; старі документи більше не виглядають конкуруючою активною специфікацією.

## Пакет 2. Три вертикальні захисні сценарії

**Мета:** зловити саме клас «одне вилікували — сусіди зламалися», а не наростити лічильник тестів.

### A. Звичайна операція

Свіжий синтетичний користувач і рахунок → PWA draft → відсутність DB mutation до confirm → confirm → правильна сума/баланс/history/report → повторний confirm із того самого та stale session → один ефект → cancel/void → узгоджені баланс і звіт. Порівняти підтримуваний bot write-path на тих самих інваріантах.

### B. Переказ

Два рахунки → same-currency і cross-currency → без ручного FX запис неможливий → зрозумілий напрямок курсу → preview відповідає commit → debit/credit атомарні → retry не дублює → переказ не стає витратою/доходом у звіті. Додати ризикові округлення та concurrency на реальному isolated PostgreSQL.

### C. Реєстрація й доступ

Узгоджені organic/course/partner гілки → справжній session/access resolver → cardless / pending / confirmed / replay / existing entitlement / family варіанти → точний trial snapshot і відсутність downgrade. Локальна інтеграція з контрольованим provider boundary; реальні Telegram/PSP кроки — окремий acceptance за участю власника.

**Вихід:** відтворювані команди на disposable середовищі, відомий час виконання, жодної залежності від особистої `.env` чи користувацької БД. Browser shell smoke лишається швидким smoke, не перейменовується на фінансовий end-to-end.

**Стоп-умова:** якщо Docker/browser/dependency capability недоступні, зафіксувати конкретний blocker і налаштувати ізольований шлях. Не підміняти real DB fixture-моком і не ставити зелений статус за невиконаний сценарій.

## Пакет 3. Перетворити карту на регресійний захист

- Прив’язати кожну зміну до impacted FLOW/INV та конкретних тестів. Список файлів — підказка, не повна модель впливу.
- Додати named scenario evidence до наявного `validate`/delivery механізму окремим погодженим PR; не будувати паралельний пайплайн.
- Явно рахувати executed/skipped/blocked. Перевірки, які поза isolated runner завжди skipped, не мають створювати ілюзію пройденого покриття.
- Вибрати family owner/member і modality upload→review→confirm→DB як наступні ризикові перетини.
- Не видаляти source-contract тести гуртом. Заміщувати їх поведінковими там, де вони зараз є єдиним захистом.
- Розвести fast feedback і production acceptance. Не запускати всі важкі перевірки для кожної дрібниці; не прибирати потрібні gates для ризикового write-path.

**Вихід:** на зміну правила видно, які сценарії захищаються і що ще не перевірене; приймання можна відтворити за exact candidate.

## Пакет 4. Прибирати костилі по одному seam

Вибирати найменший доменний seam із characterization-доказом. Для першого фінансового seam порівняти два підходи: спільна pure domain policy зі збереженням двох адаптерів або один внутрішній commit API. Врахувати транзакційність, доступність admin service, retry/backward compatibility й bot support policy. Не оголошувати API-first єдиним правильним рішенням до spike/ADR.

Послідовність кожного такого PR:

1. Зафіксувати поточну поведінку та відомі відмінності.
2. Узгодити, які відмінності — помилки, а які — підтримувана семантика.
3. Виділити правило/адаптер без зміни продуктового результату.
4. Порівняти результати старого й нового шляху у контрольованому середовищі.
5. Перевірити sibling flows; прибрати старе тільки після трасування usages.
6. Нову бізнес-поведінку вводити окремою зміною.

Після domain seams — вузька декомпозиція PWA JS і bot orchestration. Кількість рядків — сигнал для дослідження, не самостійна причина переписування.

**Вихід:** менше місць, де треба синхронно змінювати одне правило, без прихованого скорочення підтримуваних сценаріїв.

## Пакет 5. Людський контроль і підтримка порядку

- Узгоджений GitHub backlog: owner, priority, FLOW/INV, blocked-by, acceptance, release state. Не окремий вручну синхронізований backlog у кожному чаті.
- Dashboard: поточна робота; рішення власника; deployed-but-unaccepted; наступний готовий slice; посилання на докази. Статичний dashboard цього аудиту — прототип представлення, не живий GitHub Project.
- Для кожного регресійного дефекту: який invariant пропустили, який sibling зачепили, який поведінковий guard додано. Не дописувати історію в загальний `CURRENT_STATE.md` без кінця.
- Контракти оновлюються тим самим PR, що змінює поведінку; ADR лише для справжніх рішень з альтернативами, не для кожного перейменування.
- Реєстр конфігурації/процесів: тільки несекретні імена, власник і вплив; обґрунтоване видалення після usage-перевірки. Не вбивати процеси і не читати `.env` під виглядом прибирання.

**Вихід:** нова людина/агент знаходить актуальну вимогу й перевірку без археології по чатах; власник бачить незакритий результат без читання CI-логів.

## Перша практична ітерація

Не починати всі пакети одночасно. Рекомендована черга:

1. Погодити три рішення: trial/card policy; Telegram capability policy; канонічне місце контрактів.
2. Опублікувати docs-only baseline і backlog.
3. Реалізувати один вертикальний acceptance — normal transaction з repeat/cancel і перевіркою балансу/звіту.
4. Додати transfer/FX sibling matrix.
5. Лише після цього вибрати й виконати перший domain seam.

Завершення ітерації доводять посилання на узгоджений контракт, exact candidate, passing named scenario та список явних винятків. Відсоток «проєкт дорослий» не обчислюється: початкового quality baseline ще немає.
