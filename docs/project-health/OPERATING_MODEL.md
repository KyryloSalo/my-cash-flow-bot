# Робоча модель: одна команда, а не багато паралельних здогадок

**Статус:** пропозиція до погодження, не нове правило production. Підстава — аудит `f2e53b659cee68da7d1cfb6ebabd89384fe180e2` від 19 жовтня 2026 року. [Початкова сторінка](README.md).

## 1. Що має змінитися для людини

Людина відкриває одну сторінку і бачить: що справді працює; що лише задеплоєно; які перевірки не виконані; що робимо наступним; яке рішення потрібне саме від неї. Агент відкриває ту саму задачу і отримує точні вимоги, межі, зачеплені сценарії та критерії приймання — не весь літопис проєкту.

Завдання — скоротити повторну роботу, а не імітувати штат великої компанії. Не створюємо новий трекер, новий CI-сервіс, мікросервіси чи постійно активну «раду агентів».

## 2. Джерела істини та конфлікти

До погодженої міграції чинні `AGENTS.md` та зовнішній `docs/CURRENT_STATE.md` не скасовуються цим документом. Саме розташування нового файла не робить його затвердженою вимогою.

| Питання | Запропоноване канонічне місце | Хто затверджує |
|---|---|---|
| Чого хочемо від продукту | Версійований контракт відповідного сценарію в Git-репозиторії | Власник продукту |
| Що реалізовано | Код + поведінкові тести точного SHA | Розробник і незалежний reviewer |
| Що зараз у production | GitHub deployment evidence + readback | Release owner |
| Що користувач реально пройшов | Acceptance evidence із середовищем, когортою, SHA та межами | QA; власник для реальних карток/ідентичностей |
| Що робимо далі | GitHub Issues/Project; до публікації — локальний початковий реєстр | Власник + інтегратор |
| Чому вирішили саме так | Короткий ADR або рішення в задачі, зв’язане з контрактом | Власник відповідного рішення |
| Локальний хід конкретної роботи | Наявний `delivery.py`, `.hermes/delivery/` | Інтегратор; не комітити локальні receipts |

Код доводить поточну реалізацію, але не автоматично правильність вимоги. Тест, який повторює помилкове очікування, не розв’язує конфлікт. При розбіжності: показати два джерела, назвати наслідок, отримати рішення, оновити один контракт, потім поведінку й тести. Не «узгоджувати» мовчки документацію під зручний код.

Міграція документів — окрема задача: обрати компактний чинний текст; зберегти походження; поставити в старому місці посилання/статус; перевірити всі inbound links. Не переносити весь зовнішній літопис у `main` одним комітом. Автоматично застосовувати патчі з release JSON без перевірки поточного тексту не можна.

## 3. Мінімальний контракт сценарію

Один сценарій має стабільний ID, наприклад `FLOW-TX`, і відповідає на питання:

1. **Навіщо та для кого:** користувач, права, personal/family scope, очікуваний результат.
2. **Входи:** PWA, API, Telegram recovery; первинним інтерфейсом лишається PWA.
3. **Стани й переходи:** початок → чернетка → явне підтвердження → запис → результат; cancel/retry/replay/expiry.
4. **Інваріанти:** що ніколи не повинно порушитися; права, суми, валюта, одноразовість.
5. **Побічні ефекти:** таблиці, зовнішні виклики, повідомлення, кеш, фонові задачі.
6. **Невдалі гілки:** timeout, подвійне натискання, втрачена сесія, відсутня картка, застаріла чернетка, чужий scope.
7. **Спостереження й очікування окремо:** observed at SHA / agreed target / open decision. Невідоме не записується як факт.
8. **Приймання:** поведінковий тест і, де потрібно, реальний browser/provider крок; де лежить доказ і чого він не доводить.

Не дублювати детальні вимоги в dashboard, PR, кількох чатах і тестових константах. Dashboard показує статус і посилання на контракт.

## 4. Черга роботи та передача відповідальності

Рекомендований життєвий цикл задачі:

`triage → needs_decision | ready → in_progress → review → acceptance → ready_to_release → deployed_unaccepted | verified → closed`

- `needs_decision`: є чітке питання, варіанти, власник і наслідок; агент не вгадує відповідь.
- `ready`: є бажана поведінка, межі, зачеплені FLOW/INV ID, критерії та реальна команда приймання.
- `review`: reviewer бачить оригінальну вимогу, а не лише реалізаційний переказ.
- `acceptance`: виконується названий користувацький маршрут; пропущений крок явно позначений.
- `deployed_unaccepted`: артефакт активований, але критичний acceptance ще не пройдено. Не закривати як готову функцію.
- `verified`: відповідний результат підтверджено для заявленого середовища. Для docs-only це перевірені документи, не реліз продукту.

Локальний реєстр цього аудиту — стартове наповнення, а не вже створені GitHub Issues. Під час публікації кожна активна робота отримує issue ID; далі статус змінюється в одному місці. Історичний snapshot залишається історичним, не видається за live dashboard.

**Ліміт незавершеної роботи:** один активний змінювач спільного домену; друга задача допустима лише в незалежній області/окремому worktree. Читання і рев’ю можуть йти паралельно. Не запускати декілька реалізаторів на `bot_main.py`, `miniapp/services.py`, `views.py` чи `index.html` одночасно. Це пропозиція організації роботи, не автоматично змінене налаштування системи.

## 5. Ролі агентів без постійного «штату»

| Роль | Коли потрібна | Вхід → вихід | Чого не може робити |
|---|---|---|---|
| Власник продукту — людина | Семантика, тарифи, межі доступу, спірні вимоги | Питання з варіантами → зафіксоване рішення | Не зобов’язаний сам знаходити технічний контекст |
| Інтегратор — основний агент | Кожна задача | Оригінальний запит → контракт, вузький контекст, інтегрований результат, статус доставки | Приховувати blockers, самовільно змінювати scope чи роздавати production-доступ |
| Requirements/domain analyst | Невизначені або фінансові зміни | Сценарій + код → decision gaps, інваріанти, impact map | Придумувати бізнес-правила замість власника |
| UX reviewer | Зміни PWA, onboarding, paywall, форм і помилок | Контракт → стани, тексти, mobile/browser acceptance | Вважати screenshot достатнім доказом бізнес-логіки |
| Implementer | Після `ready` | Узгоджений контракт → мінімальний diff у своєму worktree | Рефакторити сусідів «заодно», обходити gate, міняти старі очікування без рішення |
| Незалежний QA/reviewer | Значні/ризикові зміни | Оригінальний запит + exact candidate → перевірені результати й незакриті вимоги | Приймати self-report автора як доказ або ставити зелений статус пропущеному сценарію |
| Release owner | Production-bound зміни | Перевірений SHA → approval, deployment evidence, readback | Деплоїти recovery/local tree, змішувати merge й activation |

Для простих задач: інтегратор/виконавець + незалежна перевірка за чинними правилами; не шість агентів. Для фінансів/auth/billing: domain review і незалежний QA. UX reviewer підключається лише коли змінюється інтерфейс. Сильна модель — на невизначеність і ризик; механічна робота — дешевшому ізольованому виконавцю. Не змінюємо налаштування моделей або профілів цим планом.

Пакет передачі агенту: issue/requirement ID; exact base SHA; allowlist файлів; relevant FLOW/INV; заборони; acceptance-команда; очікуваний формат доказу. Відповідь агента — висновок, а не production-факт; інтегратор перевіряє результат.

## 6. Контроль регресій: менше ритуалів, більше поведінки

Використовуємо наявні `delivery.py`, `validate` та exact-SHA production workflow. Новий паралельний delivery engine не потрібен. Наявність smoke, lint або великої кількості тестів не замінює named scenario.

### Рівні перевірки

- **Швидкі unit/contract checks:** чисті правила, суми, округлення, права, переходи; запускаються для зачепленого домену.
- **Postgres integration:** реальна транзакційність, constraints, rollback, idempotency і гонки; тільки disposable DB, не локальна користувацька база.
- **PWA browser journeys:** реальні DOM, session, endpoint і БД для відібраних критичних маршрутів. Перевіряємо результат/відсутність запису, а не лише текст кнопки.
- **Provider/owner acceptance:** реальні Telegram login, PSP card binding, реальні пристрої — окремий явно дозволений крок. Моки доводять локальну гілку, але не провайдера.
- **Production readback:** SHA/health/routes — лише доказ доставки й доступності, не проходження всіх бізнес-сценаріїв.

Source-text assertions можна залишити для вузьких контрактів структури. Не рахувати їх еквівалентом інтеграційного покриття та не видаляти wholesale до заміни потрібних гарантій.

### Приклади матриць ризику

**Реєстрація/доступ:** organic / course / partner; новий / існуючий користувач; картка відсутня / bind pending / confirmed; власний / family доступ; повторний callback; прострочений стан. Очікування визначає затверджений контракт; не автоматично будувати повний декартів добуток.

**Фінансовий запис:** expense / income / transfer / cancellation / debt; UAH / інша валюта; cancel / retry / double confirm; personal / family; два паралельні підтвердження; застаріла чернетка. Обрати ризикові перетини й golden path, а не тисячі формальних комбінацій.

**Release:** зміна вимоги → impacted flows → tests → exact artifact → deployment → acceptance. Невідповідність будь-якої ланки — видимий blocker, не ще один «успішний» тест.

### Дві швидкості

Docs-only і локальна навігація: посилання, узгодженість, незалежний огляд; без product redeploy. Ризикові фінансові/auth/billing/schema зміни: RED для bugfix, поведінкова інтеграція, impacted-flow acceptance, незалежний reviewer, поточні production gates. Не вимагати фінансовий end-to-end для виправлення орфографії; не послаблювати його для зміни списання.

## 7. Безпечний рефакторинг старих костилів

Спочатку behavior characterization, потім вузький seam, потім перенесення відповідальності без зміни семантики, потім окремий PR на нову поведінку. Відокремлювати бізнес-рішення від механічного перенесення.

Обирати seam за повторними дефектами та дубльованими write-path, а не за кількістю рядків. Першими кандидатами є підтвердження/ідемпотентність фінансових записів і єдиний resolver доступу; точний перший seam визначає окрема перевірка реалізації. Не оголошувати всі legacy-модулі мертвими за назвою: спочатку imports, routes, jobs і usage, потім рішення про deprecation.

Реєстр змінних містить **лише назву/призначення**, компонент, тип, default policy, source, вплив на сценарії, validation і retirement owner. Жодних значень секретів або читання credential-файлів. Реєстр процесів містить entrypoint, port/queue role, owner, start/stop procedure і health check; не завершуємо невідомі процеси під час аудиту.

## 8. Метрики, які не заохочують імітацію

Початкові значення не вигадуються; перший етап має зібрати baseline.

- Reopen/regression: які вже прийняті FLOW повторно зламалися після зміни; не загальна кількість «червоних» unit tests.
- Acceptance debt: які deployed-функції досі не пройшли заявлений browser/provider сценарій і скільки часу це відкрито.
- Lead time: від `ready` до перевіреного результату; окремо час очікування рішення, review й owner acceptance.
- Requirement traceability: частка **зачеплених у зміні** вимог з живим acceptance-доказом; не вигаданий відсоток усього продукту.
- Flaky checks і час перевірки: що змушує повторювати незмінений кандидат; виправити причину, а не додавати повторні запуски.

Короткий перегляд: один пріоритет; одне рішення для власника; що заблоковано; який дефект потребує контрактного тесту. Якщо поле чи перевірка не змінює рішення і дублює інше — прибрати її після погодженого спрощення. Успіх — не більше Markdown або агентів, а менше повторних регресій і коротший шлях до доведеного результату.
