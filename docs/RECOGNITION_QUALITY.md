## Private disk quota

### Protected production operator

The manual `recognition-operator.yml` workflow accepts only `status`, `activate` or `disable`, an exact already-deployed SHA and matching `recognition-<action>` confirmation. It runs only from the current protected `main`, requires the existing `production` Environment approval, uses the production concurrency group and verifies successful validation/deployment evidence. This is not a replacement deployment route.

The fixed-purpose remote script takes the same host lock as deployment, verifies `current-release`, the release path and healthy exact-SHA service image tags, and checks that admin and cleanup worker share the same private named volume. It never reads container environments or renders resolved compose configuration. Disable needs only the admin service, not healthy storage/worker/beat. There is no export action or raw-data artifact upload.

The runtime `recognition_quality_operator --action activate` validates private-root restrictions, disk headroom, notification settings and private export authorization; performs an exclusive synthetic write/read/unlink probe within the quota; and sends a sanitized real administrator-channel delivery probe before enabling all-photo mode and the seven-day text/voice cohort. An already-active text/voice cohort is never extended or enlarged. Output includes `all_images_enabled` and aggregate operational metadata only; a separate status invocation reads back the write. Failures are sanitized. The admin API and cleanup worker explicitly configure the same persistent root in compose. Activation is not proof that real PWA photo/audio examples or a private analyst retrieval path have passed acceptance.

- Configure `RECOGNITION_QUALITY_STORAGE_ROOT` as an absolute, dedicated, persistent private directory, shared by every API/worker replica using this database. Do not use static/media directories, a public web-server mount, an ephemeral container layer or a symlink. Without this directory, media capture is skipped without stopping recognition; text/metadata collection can continue.
- The hard ceiling is **1 GiB (1,073,741,824 bytes)** of actual files in the private directory, including raw audio/photo, private review exports and orphans. This is disk usage, not a RAM allowance, DB row count or physical server-space reservation. Database metadata/text and filesystem overhead are outside this file quota. Provision free server disk and the persistent mount separately during approved rollout; compose does not allocate production storage automatically.
- The config defaults to 1 GiB and may lower the limit for testing; it cannot raise the hard ceiling. Each media file is additionally bounded to 10 MiB. Postgres stores the opaque file key and byte count, not raw media blobs.
- PostgreSQL transaction advisory locking serializes the scan/check/write across workers and cohort-config changes. The scan counts actual file lengths, including orphaned files, rather than trusting only DB accounting. No blob collection is loaded into RAM to count usage.
- Files have random names, no user IDs/extensions, and POSIX mode `0600`; the root is `0700`. Deployment must verify actual filesystem/web-server access restrictions (Windows requires equivalent ACLs).
- When the next file would exceed quota it is not saved. Recognition continues, no extra inference is requested, and existing financial confirmation gates are unchanged. Storage or notification failures do not create financial writes or turn telemetry into a request failure.

## Telegram administrator notifications

The existing admin-notification Celery task sends a warning at **90%** and a full/insufficient-space alert at the limit or when the next file cannot fit. `ADMIN_NOTIFICATIONS_ENABLED`, configured `ADMIN_TELEGRAM_IDS`, bot access and a working Celery broker/worker are prerequisites; no new credentials are embedded in this feature.

Storage warning/full messages contain only aggregate operational metadata. They never include raw media or user identity and are each rate-limited for 24 hours. Their durable outbox is retried every five minutes.

The authorized all-photo feature separately queues each captured original as a Telegram document, without recompression, for each configured administrator. Captions contain the Telegram user ID, source, current recognition/outcome status and a bounded short result. They do not include raw provider responses. The photo outbox contains only an opaque capture reference, not another media copy; sends are queued after transaction commit. Delivery waits for the recognition outcome for up to two minutes; if parsing crashes, periodic recovery still sends the original with `pending` status. Beat retries queued/failed photo sends every minute. Already-sent rows are skipped; independent recipients retain independent delivery state. Delivery is at-least-once: a remote success followed by a database/process failure can still duplicate a send. Successful enqueueing is not delivery evidence. Inspect outbox state and perform an approved admin-channel smoke after rollout. Already-delivered Telegram copies are outside private-storage deletion and must be handled by the administrator.

## Retention and deletion

Before activation or status, the operator verifies the pinned, healthy Compose PostgreSQL container and probes the actual worker connection. Both the Psycopg wire-peer IP/port and SQL server IP/port must match the verified database target, with PostgreSQL 16 metadata available; an unverified peer, including a pooler forwarding SQL to that target, fails closed. The protective `disable` path bypasses this new database prerequisite. This gate passed during the approved activation and status readback above; it does not establish recipient-side download integrity.

The shipped photo-delivery hardening persists the per-configured-administrator outbox even while `ADMIN_NOTIFICATIONS_ENABLED` is false; pausing delivery does not discard the capture reference. Each send is claimed in a short database transaction with a five-minute lease, and private-file reads and Telegram HTTP run outside that transaction. A dedicated PostgreSQL session holds a per-outbox advisory mutex through claim, HTTP and finalization, so lease expiry alone cannot start a competing send while the first session remains connected. The session closes on exit, and PostgreSQL releases its lock on disconnect/crash; recovery can then reclaim an expired lease and fences stale worker results. This requires direct/session-affine PostgreSQL connections, not transaction-pooling middleware. Network failures retry after 60, 120, 240, 480 and 960 seconds; the sixth failed attempt becomes a terminal `dead` outbox row and emits the sanitized `recognition_photo_delivery_exhausted` operational error. Invalid/missing private originals become terminal immediately. Dead letters need operator investigation, not automatic infinite retry. Deletion revokes queued claims and prevents a send not yet started; an already-started Telegram request cannot be recalled. Lost database sessions or ambiguous Telegram responses can still duplicate remote effects: this does not promise exactly-once delivery or retraction of remote copies. The fields require `admin_notifications.0002_photo_delivery_reliability`; deployment and activation evidence above, not local tests, establish the active release.

Celery beat schedules `miniapp.tasks.purge_expired_recognition_captures_task` hourly. With beat and workers running, expired text/voice cohort captures and captures older than the configured retention (at most seven days) are removed. Text/voice cohort expiry does not prematurely remove recent all-photo samples. Files are unlinked only after DB deletion commits; an aborted deletion preserves them. Old crash/rollback orphans are also swept and count against quota until removed. Filesystem removal failures are best-effort and continue to consume quota until a later orphan sweep succeeds. The private directory must remain available to API and cleanup workers.

`hard_delete_user` deletes recognition metadata, removes pending photo-notification references and schedules media removal after DB commit. ORM capture deletion has the same cleanup hooks. Both paths invalidate cached review exports after commit; private exports otherwise expire after one hour. Rollback preserves files. Filesystem failures remain an operational cleanup issue, not proof of deletion. Already-delivered Telegram copies are not automatically retracted.

The shipped hardening routes account capture removal through the same ORM cleanup used by retention and direct capture deletion. Regression tests cover removal of queued, failed and processing photo-notification references. A legacy outbox row whose capture or media reference is absent becomes terminal `dead` with the sanitized `recognition_photo_capture_missing` reason, clears its stale payload and lease/retry fields, and is not retried. The approved deployment and activation readback above establish rollout; these regressions alone do not.

Migration `0022_recognition_private_disk` refuses to drop a nonempty legacy DB-media field. If legacy raw blobs exist, stop and arrange reviewed private migration; do not bypass the guard or discard captured data.

## Analysis/export release gates

The export service requires authenticated protected access, bounds rows to 1000 and excludes the explicit raw-text/media fields by default. Provider/normalized/correction fields can themselves contain sensitive text, so **all exports are private**, even without `include_raw`. Explicit raw export reads private files and bounds aggregate media bytes to 20 MiB; it must not be put into logs, Telegram, GitHub Actions or broad data exports.

The internal service requires an active Django superuser and additionally checks the shared token only when configured. On the authenticated private server, `python manage.py recognition_quality_export --requester-id <active-superuser-pk> --limit 100` writes one bounded random `*.export.json` file under the private root with mode `0600`; stdout prints filename/count/has_more only. `--metadata-only` excludes explicit raw fields. Exports count against the same quota and expire after one hour or capture/account deletion. This local operator CLI must never become an unauthenticated HTTP wrapper or run in GitHub Actions. Do not send private exports or non-photo raw samples via Telegram or broad exports; original receipt photos are the explicit administrator-notification exception above. Production private analyst access remains unverified. Weekly AI analysis stays paused until that access and target-environment acceptance pass. `unreviewed` is not accuracy; no model training or production recognition-accuracy claim is made.
